# Security controls — 16 October 2026

## Dependencies

The vulnerable `fast-glob → micromatch → braces` build-time chain is removed. A version-scoped npm override gives `vite-plugin-dynamic-import@1.6.0` a small adapter to `tinyglobby@0.2.17`, already used by Vite. The plugin calls only `sync(patterns, { cwd })`; compatibility tests cover its extension lists, recursive patterns, exclusions and missing matches. This adapter is not a complete fast-glob replacement. Recheck the call site when upgrading the plugin and remove the adapter when upstream no longer needs it.

`npm audit` reports no known vulnerabilities. `scripts/dependency-audit.mjs` accepts no advisory exceptions or expiry extensions. `build-safety.ts` also rejects build-only dependencies in browser and Worker bundles. Build servers and source/config inputs must remain trusted; never expose Vite's development server publicly. A clean dependency audit is not proof that an application has no security flaws.

## Access and browser responses

Cloudflare Access protects the entire Worker, including production and preview URLs and static assets. An explicit email allowlist receives one-time login codes; sessions last eight hours. There is no public registration or app password database. A separate Service Auth policy accepts only the release verification credential, held in Infisical. API and health endpoints have the same gate as the interface. No public health bypass is configured.

Production scripts require a fresh CSP nonce generated by the Worker and propagated through vinext's streamed response. Incoming CSP headers cannot select that nonce. HTML and RSC responses use `private, no-store` and disable CDN caching; fingerprinted assets retain their normal caching. The policy restricts connections to the same origin and the optional MapTiler provider, forbids plugins, base URL changes and framing, and allows local/blob map workers. Inline styles remain permitted because the charts and animation library set element styles. Only the local Vite development policy permits inline/evaluated scripts for HMR.

## Request and provider budgets

Per-client limits and persistent global budgets remain active after login: 240 API requests/minute, 6,000/hour, 40,000/day and 600,000/month. Open-Meteo has a separate weighted budget of 120/minute, 1,000/hour, 6,000/day and 100,000/month. Counters are atomic and survive restarts. Every outgoing weather attempt reserves capacity; a failed budget service blocks requests. Authorized clients can still exhaust a shared budget and temporarily deny service.

Market APIs only read D1; users cannot trigger Fingrid/ENTSO-E calls. The collector persists rolling quotas, spacing and cooldowns. Fixed provider hosts, redirect rejection, deadlines, body limits, bounded pagination, finite-number validation and parameterized SQL protect trust boundaries. The API validates geography and date ranges server-side. XML declarations/entities are rejected. Errors expose safe codes and request IDs only.

Device coordinates remain in bounded POST bodies, outside shared caches, URLs, D1 and logs. Traces are disabled to avoid logging upstream token query strings. The Worker has no public administrative collection or database endpoint.

## Credentials and validation limits

Infisical owns secrets. GitHub uses workflow/environment/ref-bound OIDC; only provider credentials reach Worker secrets. The Access verification secret stays in the deployer, outside Terraform inputs and state. The invitation list and service token ID are configuration; private Terraform state contains them. Builds have no provider credentials and CI scans source history. D1 uses EU jurisdiction and authorized bindings/administration; Terraform state is in private R2.

The deployment is a non-commercial evaluation using Open-Meteo's public endpoint under its [terms](https://open-meteo.com/en/terms). Before commercial use, obtain the appropriate plan and set `WEATHER_PROVIDER_MODE=customer` with `OPEN_METEO_API_KEY` in Infisical prod. Deployment rejects customer mode without a key; possession of a key alone does not prove entitlement to historical or model-run features.

Automated checks cover dependencies, configuration, response headers, browser functionality and access denial/authenticated probes. Penetration testing, load testing and real-device Safari/iPhone testing have not been performed. These controls do not guarantee provider correctness or complete protection against abuse.
